# 订单重点追踪事项步骤调整——前端对接说明

## 1. 结论

`OrderTrackingFormDialog.vue` 和 `TrackingItemCard.vue` 当前已经按照
`GET /order-tracking/options` 返回的选项动态生成下拉框和进度条，不需要写死或手工增加步骤。

本次没有修改：

- Controller 路径；
- 请求、响应字段名；
- `typeValue`、`statusValue` 的提交结构；
- 模块编码；
- 日志、图片、等待回复和保存接口。

前端仍应通过 `sortNo` 排序后的接口结果渲染步骤，并以 `value` 作为选项值。

## 4. `OrderTrackingFormDialog.vue` 检查项

当前实现满足以下要求，建议保留：

```vue
<TrackingItemCard
    :status-options="getModuleStatusOptions(module)"
/>
```

```javascript
function getModuleStatusOptions(module) {
    const moduleForm = moduleForms[module.moduleType]

    if (!module.hasType) {
        return getStatusOptions(optionMap.value, module.moduleType)
    }

    return getStatusOptions(
        optionMap.value,
        module.moduleType,
        moduleForm.typeValue
    )
}
```

不要在前端按照状态码大小计算进度，也不要写死“共四步/五步”。应继续使用接口数组的位置计算当前步骤。

## 5. 历史数据

执行配置停用前，增量脚本会先迁移订单主表中的当前状态：

- `sticker_status: 3500 → 3400`
- `inner_box_status: 5500 → 5400`
- `color_box_status: 7500 → 7400`
- `carton_status: 1500 → 1400`

这一步不可省略，否则编辑旧订单时，后端会把已停用状态纠正为该流程的第一步。

历史日志的 `before_status`、`after_status` 不迁移。日志中已经保存的
`3500`、`5500`、`7500`、`1500` 仍可由后端翻译为“检查无误”，但它们：

- 不再出现在新增或编辑页面的选项中；
- 不再被后端认定为新流程的有效可提交状态；
- 不需要前端增加兼容选项。

## 6. 上线操作

   `GET /order-tracking/options`
